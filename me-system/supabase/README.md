# Supabase database

The Monitoring and Evaluation System database for Supabase (Postgres 15+). It implements the
Level 3 data dictionary (`docs/DATA_DICTIONARY.md`) and loads the National Cashew Policy example.

Status: **live** in Supabase project `monitoring-evaluation-system` (ref `cvutbidnazfgfbeptnbz`, Singapore,
free plan, https://cvutbidnazfgfbeptnbz.supabase.co). All six migrations and the seed are applied; every table's
fingerprint matched a local build and action status for 2025 is 11 / 27 / 6. The first administrator account is set up.
Signed-in users of the website read and write Submissions, Reviews and the report form here (see "The website").

## What's here

| File | What it does |
|---|---|
| `migrations/20260927000100_schema.sql` | 29 tables, keys, allowed values, one-per-year rules, insert-only and no-delete triggers |
| `migrations/20260927000200_rules.sql` | % of target and status calculated by the database; frozen submitted revisions, published forms and reports, locked indicator versions; no self-approval; workflow functions; dashboard views |
| `migrations/20260927000300_access.sql` | Row-level security for the four pilot roles |
| `migrations/20260927000400_private_helpers.sql` | Moves the role helper functions out of the public API |
| `migrations/20260927000500_read_models.sql` | Views the website reads: who is signed in, submissions with check counts, answers, review history |
| `migrations/20260927000600_open_submission.sql` | Report form entry point: returns, creates or starts correcting a ministry's report |
| `config.toml` | Supabase CLI settings for a local stack (self sign-up off, seed = `seed/*.sql`) |
| `seed/01…05_*.sql` | Cashew workspace in five parts, run in order (generated by `scripts/build_supabase_seed.py`) |
| `checks/` | Local tests: 35 database role and workflow checks on plain Postgres, and an 18-step browser test of the website against a local Supabase stack |

### What the seed loads

- 1 policy (NCP-2022), 3 goals, 3 clusters, 17 ministries, 17 programmes, 44 actions with lead and contributing ministries
- 121 indicators (108 action, 13 outcome), each with version 1 and the 2027 target or 2022 baseline
- Reporting years 2023 to 2028 with the workbook's status thresholds (2023–2024 only hold outcome figures)
- The Kobo form, version 2026051204, with 544 questions (English and Khmer)
- Reporting year 2025: 17 approved ministry submissions, 108 answers and 108 official results. The database recalculates every % and status, and all match the workbook (actions 11 fully, 27 largely, 6 limited)
- Outcome results 2023–2025. Q1, Q2, PR1, PR2, S2 and S3 are flagged `is_test_data`

The seed **doesn't load** personal data, user accounts, evidence files, 2025 narratives (not in the workbook), or the illustrative 2026 records shown on the website.

## Applying it to Supabase

**Option A: SQL editor (no tools needed)**

1. Create a project at supabase.com. Choose the Singapore region (closest to Phnom Penh).
2. Open **SQL Editor**, then paste and run each file in order:
   1. `migrations/20260927000100_schema.sql`
   2. `migrations/20260927000200_rules.sql`
   3. `migrations/20260927000300_access.sql`
   4. `migrations/20260927000400_private_helpers.sql`
   5. `migrations/20260927000500_read_models.sql`
   6. `migrations/20260927000600_open_submission.sql`
   7. the five files in `seed/`, in order (01 to 05)
3. Run `select status, count(*) from action_status where year = 2025 group by 1;` The result should be 11 / 27 / 6.

**Option B: Supabase CLI**

```bash
cd me-system
npx supabase init            # once; keeps the existing migrations folder
npx supabase link --project-ref <project-ref>
npx supabase db push         # applies migrations/
for f in supabase/seed/*.sql; do psql "$SUPABASE_DB_URL" -f "$f"; done
```

### The first administrator

Sign up once through Supabase Auth (Dashboard → Authentication → Add user). Then run this in the SQL editor,
using the same email address:

```sql
with u as (
  insert into users (auth_user_id, email, full_name, status)
  select id, email, 'Secretariat lead', 'active' from auth.users where email = 'lead@example.org'
  returning id
), m as (
  insert into memberships (workspace_id, user_id, ministry_id)
  select w.id, u.id, mi.id from u, workspaces w join ministries mi on mi.workspace_id = w.id and mi.code = 'moc'
  where w.code = 'cashew-moc'
  returning id, workspace_id, user_id
)
insert into role_grants (workspace_id, membership_id, role, scope_type, granted_by)
select m.workspace_id, m.id, r.role::app_role, 'workspace', m.user_id
from m, (values ('admin'), ('reviewer')) r(role);
```

After that, the administrator adds the other people. A focal point's grant has `scope_type = 'ministry'` and the ministry's ID.

## How the rules are enforced

| Rule | Where |
|---|---|
| Focal points see only their ministry's submissions; the Committee sees approved results only; anonymous visitors see nothing | RLS policies, `access.sql` |
| % of target is never typed | `answers_guard` trigger calculates it (same formulas as `src/lib/rules.ts`) |
| A submitted revision never changes; corrections start a new revision | `answers_guard`, `revisions_guard`, `new_revision()` |
| One approved result per indicator and year; earlier ones kept as superseded | unique index + `decide_revision()` |
| Nobody approves what they entered, including the Administrator | `no_self_approval` trigger |
| Return and reject need a reason; approval needs four checks and no open blocking flags | `review_events` checks + `decide_revision()` |
| Review and audit logs can't be edited or deleted | `insert_only` triggers |
| Ministries, indicators, users and approved records are never deleted | `no_delete` triggers |

The app calls the workflow with `supabase.rpc('submit_revision', { rev })`,
`rpc('start_review', { rev })`, `rpc('decide_revision', { rev, decision, reason, checks, indicator_codes })`
and `rpc('new_revision', { sub })`.

## The website

The site uses two settings (Vercel → Project → Environment Variables); both are public by design:

| Variable | Value |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | `https://cvutbidnazfgfbeptnbz.supabase.co` |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | the project's publishable key (`sb_publishable_…`) |

Without them the site is the demo only. With them, signing in (email and password) switches the header to the real
account and roles, and these pages use the database:

| Page | Live behaviour |
|---|---|
| `/submissions` | Every submission the person may see (RLS), with check counts |
| `/reviews`, `/reviews/<code>` | Queue, answers, flags and review history; Approve / Return / Reject call `decide_revision` |
| `/collect/cashew-indicator-report` | Loads the ministry's report for a year; Save draft, Submit, Start a correction (`open_submission`, `submit_revision`) |

All other pages still show the example data from `src/data/cashew.json`. Evidence upload is not connected yet.

**Supabase settings to check in the dashboard:** Authentication → Sign In / Providers → turn off *Allow new users to
sign up* (accounts are created by the administrator; `config.toml` already does this for local stacks). Keep the email
provider itself enabled, or password sign-in stops working.

## Testing locally

**Database checks (plain Postgres, no Supabase account):**

```bash
PGHOST=/tmp PGPORT=5432 PGUSER=postgres supabase/checks/run_local.sh
# 35 checks passed
```

The checks sign in as a Secretariat lead (admin and reviewer), a reviewer, the MAFF focal point and a Committee member,
then run a full correction round on the MAFF 2025 report: new revision, edit, submit, review and approve.
Along the way they confirm that anything not allowed is blocked.

**Website against a local Supabase stack (needs Docker):**

```bash
cd me-system
npx supabase start -x studio,imgproxy,realtime,storage-api,edge-runtime,logflare,vector,supavisor,postgres-meta,mailpit
supabase/checks/local_test_users.sh              # lead, reviewer and MAFF focal test accounts
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321 NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<from supabase status> npm run build
NEXT_PUBLIC_SUPABASE_URL=... NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=... npx next start -p 3100
node supabase/checks/live_e2e.mjs                # 18 steps; reset with `npx supabase db reset` before a rerun
```

The browser test signs in as each account: a wrong password is refused; the focal point sees only MAFF, saves a
2026 draft, reloads it, submits, and starts a correction of the approved 2025 report; the lead approves the focal
point's report, enters an NBC report and is blocked from approving it; the second reviewer returns it with a query
and is refused the Administration page.

## Regenerating the seed

```bash
python3 scripts/build_supabase_seed.py
```

IDs are deterministic, so regenerating the seed doesn't change keys.
